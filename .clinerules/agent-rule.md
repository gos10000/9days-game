# Agent 工作规则

## 0. 优先级
本规则优先级：用户当次指令 > 本规则 > 代码库既有习惯。
规则之间冲突时，按下列顺序执行：文件边界 > 文档产出 > 代码规范 > 方案来源。

## 1. 文件改动边界
- 只改动与当前任务直接相关的文件。判断标准：该文件不被修改时，任务无法完成。
- 禁止“顺手”改动无关文件：格式化、重命名、删除、重构、调整 import 顺序等，均需用户明确要求。
- `Docs/agent` 以外的文档（如 `Docs/program`）由人维护，禁止修改。

## 2. 文档产出（任务完成后必须执行）
在 `Docs/agent/` 下，按**工作内容**，如是修bug统一放在`Docs\agent\debug`下；每个子文件夹内放两份 md，同目录、同名前缀：

### 2.1 人类文档 `<工作内容>.md`
- 目标读者：接手该代码的人。要求简洁、可读。
- 开头必须有简短目录（列出下文各节）。
- 必须覆盖理解和使用该代码所需的全部信息，至少包括：
  - 每个脚本/模块的职责；
  - 每个对外接口的入参、出参、返回值含义；
  - 关键参数及其作用；
  - 使用方式/调用示例（如有）。

### 2.2 Agent 文档 `<工作内容>_agent.md`
- 目标读者：后续 agent。要求详细、准确、可追溯。
- 必须记录：本次改了什么、为什么改、涉及哪些文件与函数、已知限制/待办、验证方式。
- 不追求可读性，追求信息完整与无歧义。

## 3. 代码规范
- 代码需具备可读性与可维护性：命名表意、职责单一、避免重复逻辑。
- 影响游戏表现的参数必须在 Unity Inspector 中可调（如 `[SerializeField]`），禁止硬编码。
- 注释：每个函数或独立代码块前用 1–2 行说明其功能；禁止大段注释（连续超过 3 行的注释块）。

## 4. 方案来源与询问
- 动手前先读 `Docs/program/` 下与任务相关的方案。
- 方案描述不足以支撑实现时（缺接口、缺参数、缺流程、存在歧义），**直接询问用户**，禁止自行假设或补全。

## 5. 完成前自检
- [ ] 是否只改了任务相关文件？
- [ ] 是否未触碰 `Docs/agent` 以外的文档？
- [ ] 两份 md 是否已按上述目录与命名产出？
- [ ] 人类文档是否有目录且覆盖入参/出参/脚本职责？
- [ ] 游戏参数是否已暴露到 Inspector，无硬编码？
- [ ] 是否存在大段注释？
- [ ] 方案不明确处是否已询问而非臆测？
